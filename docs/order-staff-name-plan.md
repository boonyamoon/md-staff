# แผน: แสดงชื่อคนสั่งอาหาร และคนเก็บเงินในใบเสร็จ

สถานะ: ยืนยันแล้ว ใช้ข้อเสนอในหัวข้อ 7 ทุกข้อ
แก้โค้ดขั้น 1–5 แล้ว (`pos-services` และ `myapp` branch `feat/order-staff-names`)
ยังไม่ได้รัน migration กับฐานข้อมูลใด และยังไม่ได้ลองจริง (ขั้น 6)

## 1. เป้าหมาย

| ที่แสดง | ปัจจุบัน | ต้องการ |
|---|---|---|
| รายการอาหารในหน้าโต๊ะ (iPad) | คนสร้างออเดอร์ | คนสั่งรายการนั้น |
| ใบครัว | คนสร้างออเดอร์ | คนสั่งรายการในใบ |
| ใบเสร็จ | คนสร้างออเดอร์ | **คนเก็บเงิน** (ยืนยันแล้ว) |
| ใบเปิดโต๊ะ | คนเปิดโต๊ะ | ไม่เปลี่ยน |
| ใบยกเลิก | คนที่กำลังยกเลิก | ไม่เปลี่ยน |

repo ที่แก้: `pos-services` และ `myapp` ส่วน `md-staff` ไม่ต้องแก้ เพราะ server รู้จากการ login ว่าใครส่ง

## 2. ผลตรวจโค้ด

- `sales_order_items` ไม่มีช่องเก็บคนสั่ง ต้องเพิ่ม
- `payments.created_by_id` มีใน schema อยู่แล้ว แต่ขายตรง ปิดบิลพัก QR Beam และคืนเงิน ไม่ได้บันทึกค่า จึง**ไม่ต้อง migrate ฝั่งการรับเงิน**
- iPad ไม่มีช่องคนเก็บเงินใน `Payment` และไม่ได้ส่งค่าขึ้น server
- iPad อ่านออเดอร์จาก server ด้วย `OrderQueryService.getOrderDetails` (ใบครัวของ staff app ก็ใช้ทางนี้) ซึ่งระบุทีละ field จึงต้องเพิ่มเอง

## 3. กติกา

### คนสั่งรายการ (`ordered_by_id`)

| กรณี | ค่าที่บันทึก |
|---|---|
| staff app | คนที่ login เครื่องนั้น |
| iPad เพิ่มรายการ | คนที่ใช้ iPad อยู่**ตอนเพิ่มลงตะกร้า** |
| ลูกค้าสั่งผ่าน QR / kiosk | ว่าง (QR แสดง "Seat …" ตามเดิม) |
| แอปรุ่นเก่าไม่ส่งมา | ว่าง ไม่เดา |
| รายการที่บันทึกบน server แล้ว | **ไม่เปลี่ยนอีก** แม้คนอื่นแก้จำนวนหรือบันทึกซ้ำ |
| คัดลอกออเดอร์ | คนที่กดคัดลอก |

ที่โต๊ะหรือบิลที่ส่งครัว ถ้าคน B กดสินค้าเดียวกับรายการที่คน A เพิ่มไว้แต่ยังไม่ส่ง จะ**แยกเป็นคนละบรรทัด**
การขายหน้าร้านแบบไม่ส่งครัวยังรวมบรรทัดตามเดิม

### การแสดงชื่อคนสั่ง

1. รายการจาก QR: "Seat …"
2. มี `ordered_by_id`: ชื่อคนนั้น ถ้าหาชื่อไม่ได้ ไม่แสดง (ดีกว่าแสดงผิดคน)
3. ไม่มีค่า (ข้อมูลเก่า): คนสร้างออเดอร์ ตามเดิม

ใบครัวหนึ่งใบมีหลายคนสั่ง: แสดงทุกชื่อคั่นด้วยจุลภาค ส่วน sticker ใช้ชื่อของรายการนั้น

### ชื่อในใบเสร็จ

| กรณี | ชื่อที่แสดง |
|---|---|
| ใบเสร็จปกติ และพิมพ์ซ้ำ | คนที่บันทึกการรับเงินครั้งล่าสุดที่สำเร็จ |
| ใบคืนเงิน | คนที่ทำรายการคืนเงินล่าสุด |
| ใบยกเลิกบิล (void) | คนเก็บเงินเดิม |
| บิลก่อนจ่าย | คนที่กดพิมพ์ (ข้อ 7.1) |
| บิลเก่าที่ไม่มีข้อมูล | คนสร้างออเดอร์ ตามเดิม |

QR Beam: บันทึกคนที่กดสร้าง QR เพราะการยืนยันจาก Beam ไม่มีพนักงานเกี่ยวข้อง

## 4. pos-services

### 4.1 ฐานข้อมูล

migration ใหม่: `sales_order_items.ordered_by_id uuid NULL` ไม่ใส่ foreign key และไม่เติมข้อมูลย้อนหลัง
(แบบเดียวกับ `performed_by_provider_id`) เพื่อไม่ให้การขายล้มเพราะข้อมูลพนักงาน

### 4.2 จุดบันทึก

ค่าจาก client ต้องเป็นพนักงานของธุรกิจเดียวกัน ถ้าไม่ใช่ให้เก็บว่าง **ห้ามปฏิเสธการขายหรือการรับเงิน**

| ไฟล์ | สิ่งที่ทำ |
|---|---|
| `MobileOrderService` | staff app: ใช้ `staffContext.staff_id` ส่วน QR เก็บว่าง |
| `HeldOrderService.holdBill` | เส้นทางนี้**ลบรายการแล้วสร้างใหม่** ต้องจำค่าเดิมตาม item id ก่อนลบ แล้วใส่กลับ |
| `HeldOrderService.holdAndSend` | ใส่เฉพาะตอนสร้างรายการใหม่ ห้ามอยู่ในข้อมูลที่ใช้ update |
| `SalesOrderService` (ขายตรง) | รับ `ordered_by_id` ของรายการ และ `created_by_id` ของการรับเงิน |
| `SalesOrderProcessingController.completeHeldOrder` | รับ `created_by_id` ของการรับเงิน |
| `BeamPaymentController` / `BeamPaymentService` | รับ `staff_id` (ไม่บังคับ) ตอนสร้าง QR |
| `RefundService` | คำขอมี `processed_by_id` อยู่แล้ว นำมาบันทึกในการจ่ายคืน |
| `types/sales-order.types.ts` | เพิ่ม field ทั้งสอง |

`holdAndSend` คำนวณรหัสกันส่งซ้ำจากรายการทั้งก้อน field ใหม่จึงต้องเป็น optional
และการลองส่งซ้ำต้องส่งค่าเดิม ไม่ต้องแก้วิธีคำนวณ

### 4.3 จุดอ่าน

- `getOrderDetails`: รายการส่ง `ordered_by_id`, `ordered_by_name` การรับเงินส่ง `created_by_id`, `created_by_name`
- หาชื่อด้วยคำสั่งเดียวต่อออเดอร์ ใช้รูปแบบเดียวกับ iPad (ชื่อ นามสกุล ถ้าว่างใช้ username)
- response อื่นที่ iPad นำไปบันทึกลงเครื่อง (ปิดบิล, ซิงก์, คืนเงิน, hold-and-send) ต้องส่ง field เดียวกัน

## 5. myapp (iPad)

### 5.1 ข้อมูล

- `SalesOrderItem`: เพิ่ม `orderedById`, `orderedByName`
- `Payment`: เพิ่ม `createdById`, `createdByName`
- Realm `schemaVersion` 84 → 85 เป็น field optional ใหม่ ไม่ต้องเขียนโค้ดย้ายข้อมูล
- ส่งขึ้น: `ordered_by_id` ใน `SalesOrderItemPayload` และ `created_by_id` ใน `PaymentPayload`
- รับลง: อ่านค่าใหม่ ถ้า response ไม่มีค่า **ห้ามลบค่าที่มีในเครื่อง**

### 5.2 จุดตั้งค่า

| จุด | ค่า |
|---|---|
| `POSViewModel` เพิ่มลงตะกร้า (สองเส้นทาง: ปกติ และมีตัวเลือก) | คนที่ใช้อยู่ และใช้กติกาแยกบรรทัด |
| `CurrentOrderViewModel.duplicateOrder` | คนที่ใช้อยู่ |
| `PaymentProcessor` (รับเงิน และคืนเงิน) | คนที่ใช้อยู่ |
| `RefundManager`, `SalesHistoryViewModel` (คืนเงิน) | คนที่ใช้อยู่ หรือค่าจาก server |
| สร้าง QR Beam | ส่ง `staff_id` |

### 5.3 การแสดงผล

- `TableDetailPanel`: ใช้ลำดับในหัวข้อ 3
- `OrderSlipModels`: ย้ายชื่อมาคิดจากรายการในแต่ละใบ ไม่ใช่จากออเดอร์ และส่งชื่อติดไปกับ `OrderSlipItem`
- `ReceiptData`: `cashierName` ตามตารางใบเสร็จ มีผลกับ `GeneratedReceiptView` และ `ReceiptTextFormatter` ทั้งคู่

พบระหว่างอ่านโค้ด: โหมดแยกใบครัวตามจำนวน สร้างรายการใหม่โดยไม่คัดลอก `seatLetter`
ตัวอักษรที่นั่งจึงน่าจะหายในใบแบบนั้น จุดเดียวกับที่ต้องคัดลอกชื่อคนสั่ง เสนอให้แก้ไปด้วย

## 6. ลำดับงานและการทดสอบ

| ขั้น | งาน | ตรวจ |
|---|---|---|
| 1 | server: migration + จุดบันทึก | staff app บันทึกคนส่ง, QR ว่าง, holdBill บันทึกซ้ำแล้วค่าไม่หาย, holdAndSend ไม่ทับ, รหัสพนักงานผิดแล้วยังขายได้ |
| 2 | server: จุดอ่าน | response มีชื่อ และข้อมูลเก่ายังอ่านได้ |
| 3 | iPad: ข้อมูลและการซิงก์ | ส่งค่าถูก, response ที่ไม่มีค่าไม่ลบค่าเดิม |
| 4 | iPad: หน้าโต๊ะ + ใบครัว | กติกาแยกบรรทัด และชื่อในใบทุกโหมด |
| 5 | iPad: ใบเสร็จ | ทุกกรณีในตารางใบเสร็จ |
| 6 | ลองจริง | A สั่งจาก staff app, B สั่งเพิ่ม, C เก็บเงิน: หน้าโต๊ะและใบครัวแสดง A/B ใบเสร็จแสดง C |

ลำดับปล่อย:

1. รัน migration (`prisma migrate deploy`) ไม่พบขั้นตอนรันอัตโนมัติตอน deploy
2. deploy server ซึ่งต้อง merge เข้า `main` พร้อมงาน staff app ที่ยังค้าง และ migration ของ staff app อีกสามชุดต้องรันด้วย
3. ปล่อย iPad

iPad รุ่นเก่ายังใช้งานได้ระหว่างนั้น แต่ยังแสดงชื่อคนสร้างออเดอร์
งานใน `myapp` ทำบน branch ใหม่ ไม่รวมไฟล์ที่แก้ค้างในเครื่อง

นอกขอบเขต:

- เติมชื่อย้อนหลังให้ข้อมูลเก่า
- รายงานยอดขายตามพนักงาน การใช้โปรโมชัน และแจ้งเตือน Telegram ซึ่งยังอิงคนสร้างออเดอร์
- แอปอื่น เช่น `pos-web`, `pos-kotlin` (ยังไม่ได้ตรวจ)
