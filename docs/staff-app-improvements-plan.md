## 2. ออกจากระบบต้องไปหน้า sign in

**สาเหตุ:** สถานะของขั้นตอน sign in (`setupControllerProvider`) ไม่ถูกล้างหลังเข้าระบบ พอออกจากระบบ หน้า setup จึงเปิดค้างที่ขั้น "เลือกเครื่อง" และสีธีมยังเป็นของสาขาเดิม

**แก้**
- ล้างสถานะ sign in ทุกครั้งที่ session จบ ทั้งกดออกจากระบบเอง และถูกเซิร์ฟเวอร์ตัดสิทธิ์ ([session_controller.dart](../lib/features/bootstrap/session_controller.dart), [setup_controller.dart](../lib/features/setup/setup_controller.dart))
- ได้หน้ากรอกอีเมลเปล่า สีธีมกลับเป็นค่าเริ่มต้น
- กรณีถูกตัดสิทธิ์ ยังแสดงข้อความแจ้งเหมือนเดิม

**ทดสอบ:** sign in → ออกจากระบบ → เห็นฟอร์มอีเมล → sign in ใหม่ได้จนเข้าผังโต๊ะ ทั้งตอนออนไลน์และออฟไลน์

## 5. ลำดับ option เหมือน iPad

**ที่ตรวจพบ**
- กติกาของ iPad: เรียงกลุ่มตามลำดับที่ร้านตั้งในเมนู และในกลุ่มเดียวกันเรียงตามลำดับที่กดเลือก
- ตะกร้าของแอปใช้กติกาเดียวกันอยู่แล้ว ที่ต่างคือการแสดงผล: แอปต่อทุกตัวเลือกเป็นบรรทัดเดียว (`a • b • c`) ส่วน iPad แสดงบรรทัดละหนึ่งตัวเลือก
- หน้ารายการที่สั่ง **ลำดับสลับได้จริง** เพราะ API ของ staff app ไม่ได้สั่งเรียง `item_options` ทั้งที่บันทึกลำดับไว้แล้ว (`sort_order`)

**แก้**
- `pos-services`: `StaffAppOrderService.getTableDetail` เรียง `item_options` ตาม `sort_order` แล้ว `created_at` แบบเดียวกับข้อมูลที่ iPad ได้รับ พร้อมเทสต์
- แอป: แสดงบรรทัดละหนึ่งตัวเลือก ทั้งตะกร้าและรายการที่สั่ง โดยใช้ widget เดียวกัน

```text
ข้าวกะเพรา
ธรรมดา
• เผ็ดมาก
• ไข่ดาว  +10.00
x2 • หมูกรอบ  +40.00
```

ราคาท้ายบรรทัดคือราคารวมของตัวเลือกนั้นตามจำนวน เหมือน iPad และไม่แสดงเมื่อเป็น 0

**ทดสอบ:** สั่งเมนูที่มีหลายกลุ่มตัวเลือก แล้วเทียบลำดับในตะกร้า รายการที่สั่ง และ iPad

## 6. Mark as served

### iPad ทำอยู่อย่างไร (ตรวจจากโค้ด)

| เรื่อง | iPad |
|---|---|
| กดได้ที่ | **จอครัว** (ออเดอร์โต๊ะและออเดอร์อื่นในครัว) และ**คิวออเดอร์** (เฉพาะออเดอร์ที่มีเลขคิว) หน้าผังโต๊ะแสดงสถานะอย่างเดียว |
| กดได้เมื่อ | รายการเป็น **พร้อมเสิร์ฟ** เท่านั้น |
| ระดับ | ทีละรายการ (**เสิร์ฟ**) และ **เสิร์ฟทั้งหมด** ต่อรอบ ซึ่งขึ้นเมื่อทุกรายการในรอบพร้อมเสิร์ฟหรือเสิร์ฟแล้ว |
| กล่องยืนยัน | ไม่มี และย้อนกลับไม่ได้ |
| ที่บันทึก | `kitchen_order_items` ผ่าน Supabase: สถานะ, `served_at`, `updated_at` |
| แจ้ง LINE | จอครัวไม่ส่ง คิวออเดอร์ส่ง |
| อื่น ๆ | เมื่อเปิดจอครัว รายการค้างจากวันก่อนถูกเปลี่ยนเป็นเสิร์ฟแล้วเอง |

### ที่ staff app มีแล้ว
หน้ารายการที่สั่งและผังโต๊ะอ่านสถานะจาก `kitchen_order_items` อยู่แล้ว เมื่อกดเสิร์ฟบน iPad มือถือจะเห็นตอนโหลดใหม่ **ที่ยังขาดคือปุ่มกดบนมือถือ**

### สิ่งที่จะเพิ่ม (หน้ารายการที่สั่ง)
- รายการ **ส่งเข้าครัวแล้ว / กำลังทำ / พร้อมเสิร์ฟ** มีปุ่ม **เสิร์ฟ** ใช้กติกาเดียวกันทุกร้าน
- หัวรอบมีปุ่ม **เสิร์ฟทั้งหมด** เมื่อรอบนั้นยังมีรายการที่กดเสิร์ฟได้ และถามยืนยันก่อน
- กดทีละรายการไม่ถามยืนยัน
- บันทึกแล้วโหลดรายการใหม่ และผังโต๊ะเปลี่ยนเป็น "เสิร์ฟครบแล้ว" เมื่อครบทุกรายการ
- ออฟไลน์กดไม่ได้

**ต่างจาก iPad:** iPad กดได้เฉพาะ "พร้อมเสิร์ฟ" แต่บางร้านไม่มีจอครัว สถานะจึงค้างที่ "ส่งเข้าครัวแล้ว" มือถือจึงต้องกดได้ตั้งแต่ขั้นนี้ ระบบไม่มีข้อมูลว่าร้านไหนใช้จอครัวจริง จึงใช้กติกาเดียว

**ข้อควรรู้**
- ร้านที่ใช้จอครัว: ถ้ากดเสิร์ฟก่อนครัวทำเสร็จ รายการจะออกจากคิวที่ครัวต้องทำ และย้อนกลับไม่ได้
- ออเดอร์ที่ลูกค้าสั่งผ่าน QR เป็น "รอส่งเข้าครัว" จนกว่า iPad จะพิมพ์ใบครัว จึงกดเสิร์ฟได้หลังจากนั้น

### เซิร์ฟเวอร์: endpoint ใหม่
staff app เขียน Supabase เองไม่ได้ และใช้ API สถานะครัวเดิมไม่ได้ (คนละ token และต้องรู้เลขใบครัว) จึงเพิ่ม
`POST /api/v1/staff-app/tables/:floorItemId/served` รับ `session_id` และ `order_item_ids`

- ตรวจว่าโต๊ะอยู่ในสาขาของเครื่อง `session_id` ยังตรง และทุกรายการอยู่ในออเดอร์ของโต๊ะนั้น
- เปลี่ยนเฉพาะรายการที่สถานะปัจจุบันเป็น `SENT`, `PREPARING` หรือ `READY` (ตัดสินแบบเดียวกับที่หน้ารายการที่สั่งแสดง) ข้ามรายการที่ยกเลิก ยังรอส่งครัว หรือเสิร์ฟแล้ว กดซ้ำจึงไม่ผิด
- เขียน `kitchen_order_items` (สถานะ, `served_at`, `updated_at`) และสถานะบน `sales_order_items` ใน transaction เดียว เพื่อรองรับรายการที่ไม่มีใบครัว แล้วอัปเดตเวลาแก้ไขของออเดอร์
- ไม่ต้องถือสิทธิ์โต๊ะ เพราะคนยกอาหารอาจไม่ใช่คนรับออเดอร์
- ไม่ส่ง LINE เหมือนจอครัว
- ไม่ต้องมี migration

### ผลต่อ iPad (จากการอ่านโค้ด ยังต้องลองจริง)
- iPad รับการเปลี่ยนแปลงผ่าน realtime จอครัวและหน้าโต๊ะจึงเปลี่ยนเป็นเสิร์ฟแล้ว การข้ามจาก "ส่งเข้าครัวแล้ว" ก็รับได้ เพราะขารับไม่ตรวจลำดับขั้น
- การส่งออเดอร์เพิ่มจาก iPad ไม่เขียนทับสถานะครัว
- ต้องลอง: ถ้านาฬิกา iPad เดินเร็วกว่าเซิร์ฟเวอร์ iPad อาจมองว่าข้อมูลใหม่เป็นข้อมูลเก่าแล้วไม่รับ

**ทดสอบ:** เทสต์เซิร์ฟเวอร์ (ข้ามสาขา โต๊ะเปลี่ยน กดซ้ำ รายการยกเลิก รายการรอส่งครัว เสิร์ฟจากส่งเข้าครัวแล้ว) widget test ของปุ่ม และลองจริงกับ iPad
