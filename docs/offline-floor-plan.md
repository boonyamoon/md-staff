# แผน: ใช้งานออฟไลน์ + หน้าผังโต๊ะใหม่

สถานะ: ยืนยันแล้ว (ร้านมีการกด "เสิร์ฟแล้ว" และตกลงตามข้อเสนอหัวข้อ 9)
ทำขั้น 0–5 แล้ว ยังไม่ได้วัด performance บนเครื่องจริง (ขั้น 6)

ที่ต่างจากแผน: กดโต๊ะที่เครื่องอื่นถืออยู่ แอปอ่าน `tables/:id` ก่อนและไม่ยิง claim
เพราะ server นับ claim ที่ถูกปฏิเสธรวมในโควตา PIN ผู้จัดการ (5 ครั้งใน 15 นาที)

## 1. สภาพปัจจุบัน (จากการอ่านโค้ด ยังไม่ได้วัดจากระบบจริง)

| เรื่อง | ที่เป็นอยู่ |
|---|---|
| เก็บข้อมูลบนเครื่อง | ไม่มี โซน/โต๊ะ/เมนูดึงจาก server ใหม่ |
| เช็คของหมด | ยิงทุก 20 วินาที และ**ไม่หยุดแม้ออกจากหน้าเมนู** (`menuProvider` ไม่ autoDispose) คิดเป็น 180 call/ชม./เครื่อง |
| เลือกหมวด / ค้นหา | 1 call ต่อครั้ง |
| ตัวเลือกสินค้า | 1 call ต่อสินค้า และค้างใน memory จนปิดแอป (ข้อมูลเก่าได้) |
| ผังโต๊ะ | `zonesProvider` ผูกกับ session ทั้งก้อน จึงโหลดซ้ำเกินจำเป็น |
| สถานะครัว (server) | ครัวกดสถานะลง `kitchen_order_items` แต่ `tables/:id` อ่านจาก `sales_order_items` หน้ารายการที่สั่งจึงอาจไม่ขึ้น READY/SERVED |
| สีโต๊ะ (server) | `zones` ยังไม่ส่งสถานะอาหาร จึงแยก "รออาหาร" กับ "เสิร์ฟครบ" ไม่ได้ |

## 2. การเก็บข้อมูลออฟไลน์

ใช้ **ไฟล์ JSON** ใน app support directory (`path_provider` ซึ่งมีอยู่แล้วทางอ้อม)
ข้อมูลมีขนาดเล็กและกรองใน memory ได้ จึงไม่ต้องเพิ่มฐานข้อมูลหรือ code generation

| ข้อมูล | ที่เก็บ | หมายเหตุ |
|---|---|---|
| โซน, โต๊ะ, สถานะล่าสุด | `floor.json` | ไม่เก็บ claim และ lease token (หมดอายุใน 3 นาที และเป็นสิทธิ์ถือโต๊ะ) |
| หมวด, สินค้า, SKU, กลุ่มตัวเลือก | `menu.json` | |
| รูปสินค้า | disk cache ของ `cached_network_image` | มีเฉพาะรูปที่เคยแสดง เพิ่มโควตาให้พอกับจำนวนสินค้า |
| รายการที่สั่งแล้ว | ไม่เก็บ | ต้องสดทุกครั้ง |
| ตะกร้า | ไม่เก็บ (เหมือนเดิม) | นอกขอบเขต phase นี้ |

กติกาของไฟล์
- ห่อด้วย `schema_version`, `branch_id`, `fetched_at`, `etag`
- เขียนลงไฟล์ชั่วคราวแล้ว rename เพื่อไม่ให้ไฟล์พังกลางคัน
- สาขาหรือ version ไม่ตรง หรืออ่านไม่ได้ ให้ทิ้งแล้วโหลดใหม่
- ลบเมื่อออกจากระบบ

โครงสร้างโค้ด
- `data/local/json_cache.dart` อ่าน เขียน ลบ และถอด JSON ใน isolate
- repository: แยก `cached…()` กับ `fetch…()`
- controller: แสดง cache ก่อน แล้วค่อยตัดสินใจว่าจะโหลดตามตารางหัวข้อ 3
- การโหลดซ้อนกันให้รวมเป็นครั้งเดียว โหลดไม่สำเร็จให้คงข้อมูลเดิมและแจ้งบนจอ

## 3. จังหวะโหลดข้อมูล (ไม่มี timer ดึงข้อมูล)

| จังหวะ | ผังโต๊ะ | เมนู | ของหมด |
|---|---|---|---|
| login ครั้งแรก / ไม่มี cache | โหลด | โหลด | มากับเมนู |
| เปิดแอป | โชว์ cache แล้วโหลด 1 ครั้ง | โหลดถ้าเก่ากว่า 6 ชม. | – |
| กลับเข้าแอปจากพื้นหลัง | ถ้าเก่ากว่า 60 วิ | ถ้าเก่ากว่า 6 ชม. | – |
| ออกจากโต๊ะกลับมาหน้าผัง | ถ้าเก่ากว่า 60 วิ | – | – |
| สลับโซน / หมวด / ค้นหา | ไม่เรียก | ไม่เรียก | ไม่เรียก |
| เข้าหน้าเมนู | – | ไม่เรียก | ถ้าเก่ากว่า 2 นาที |
| ส่งออเดอร์สำเร็จ | โหลด 1 ครั้ง | – | – |
| กดโต๊ะแล้วชนกับเครื่องอื่น | โหลด | – | – |
| ส่งไม่ผ่านเพราะของหมดหรือสินค้าเปลี่ยน | – | โหลด | โหลด |
| ดึงลง / ปุ่มรีเฟรช | โหลด | โหลด (หน้าเมนู, ตั้งค่า) | โหลด |

- **หน้ารายการที่สั่ง:** เรียก `tables/:id` ทุกครั้งที่เข้าหน้า และเมื่อกลับเข้าแอปขณะอยู่หน้านี้ แสดง loading ระหว่างรอ ถ้าไม่สำเร็จให้แจ้ง error พร้อมปุ่มลองใหม่ ไม่แสดงข้อมูลเก่าเสมือนว่าเป็นปัจจุบัน
- การต่ออายุ claim ทุก 60 วินาทีระหว่างถือโต๊ะยังคงไว้ เพราะเป็นกลไกกันสั่งชนกัน
- ตัวเลข 60 วิ / 2 นาที / 6 ชม. เป็นค่าตั้งต้น รวมไว้ที่ `AppConfig`
- ข้อมูลผังที่เก่าไม่ทำให้สั่งชนกัน เพราะ server ตรวจ claim ทุกครั้งที่กดโต๊ะ

## 4. ออฟไลน์ทำอะไรได้

| ทำได้ | ต้องออนไลน์ |
|---|---|
| ดูโซนและโต๊ะ (พร้อมเวลาของข้อมูล) | เปิดหรือรับโต๊ะ (claim) |
| ดูเมนู ค้นหา ดูตัวเลือก (เมื่อเน็ตหลุดขณะถือโต๊ะอยู่) | ส่งออเดอร์เข้าครัว |
| จัดตะกร้าต่อ แล้วกดส่งเมื่อเน็ตกลับ | ดูรายการที่สั่งแล้ว |

ไม่ทำคิวส่งออเดอร์อัตโนมัติ เพราะโต๊ะ สต็อก และราคาต้องให้ server ตัดสิน เสี่ยงออเดอร์ซ้ำหรือผิดโต๊ะ

## 5. หน้าผังโต๊ะใหม่

รวมหน้าเลือกโซนกับหน้าโต๊ะเป็นหน้าเดียว (`floor_screen.dart`)

```
┌──────────────────────────────┐
│ ผังโต๊ะ                 ⟳  ⚙ │
│ ชั้น 1    ระเบียง    VIP       │  แท็บโซน เลื่อนแนวนอนได้
│ ━━━━                         │  เส้นใต้สี theme
│ ออฟไลน์ · ข้อมูลเมื่อ 14:32       │  แสดงเฉพาะตอนจำเป็น
│  ┌────┐   ┌────┐   ┌────┐    │
│  │ A1 │   │ A2 │   │ A3 │    │  3 คอลัมน์
│  │ ♟4 │   │ ♟4 │   │ ♟4 │    │
│  └────┘   └────┘   └────┘    │
└──────────────────────────────┘
```

การ์ดโต๊ะ: พื้นขาว, มุมมน 12, เส้นขอบ 4 dp เท่ากันทุกสถานะ, ชื่อโต๊ะตัวหนากลางการ์ด, ไอคอนคนกับจำนวนที่นั่งด้านล่าง
(สีและความหนาประมาณจากรูป ถ้ามีค่าจาก design ให้ใช้ค่านั้น)

| สถานะ | เงื่อนไข | สีขอบ |
|---|---|---|
| ว่าง | ไม่มี session | `#E1E5EA` |
| ยังไม่ได้สั่ง | มี session, ไม่มีรายการ | `#6B7183` |
| รออาหาร | มีรายการที่ยังไม่เสิร์ฟ | `#F2A33C` |
| เสิร์ฟครบแล้ว | เสิร์ฟครบทุกรายการ | `#8BC653` |

สถานะที่รูปไม่มี (เสนอ): คงสีขอบตามอาหาร แล้ววางไอคอนมุมขวาบน
กุญแจ = เครื่องอื่นถืออยู่, ดินสอ = เราถืออยู่, ใบเสร็จ = รอชำระเงิน, งดใช้ = พื้นเทาและกดไม่ได้
ยอดเงิน จำนวนรายการ และชื่อผู้ถือโต๊ะ จะไม่อยู่บนการ์ดแล้ว (ชื่อผู้ถือยังเห็นในหน้าต่างขอรับโต๊ะ)

การนำทาง: ลบ `TablesScreen` และ route `/zones/:zoneId`

## 6. Performance

- `TabBarView` กับ `GridView.builder` สร้างเฉพาะแท็บและการ์ดที่เห็น และจำตำแหน่งเลื่อนของแต่ละแท็บ
- โมเดลเปรียบเทียบค่าได้ (`==`) การ์ดแต่ละใบ `select` เฉพาะโต๊ะของตัวเอง รีเฟรชแล้ววาดใหม่เฉพาะใบที่เปลี่ยน
- การ์ดไม่ใช้เงา, `Opacity` หรือ clip ที่ไม่จำเป็น
- อ่าน เขียน และถอด JSON นอก UI thread
- เมนู: จัดกลุ่มตามหมวดและเตรียมคำค้นครั้งเดียวตอนโหลด กรองใน memory
- รูปสินค้าถอดรหัสตามขนาดที่แสดง (`memCacheWidth`)
- `ApiLogger` ไม่แปลง body ก้อนใหญ่ทั้งก้อนก่อนตัด (กระตุกใน debug)
- เกณฑ์ตรวจ: profile mode บนเครื่องจริง โต๊ะ 100 สินค้า 500 เลื่อนและสลับแท็บแล้ว frame ไม่เกิน 16 ms

## 7. งานฝั่ง server (`pos-services`)

1. `GET /staff-app/zones`: เพิ่ม `session.food_status` = `NOT_ORDERED | WAITING | SERVED` คำนวณด้วย query รวมครั้งเดียว
   - ต้องยืนยันกับข้อมูลจริงว่าสินค้าทุกรายการมีแถวใน `kitchen_order_items` ถ้าบางรายการไม่เข้าครัว ต้องกำหนดกติกาเพิ่ม
2. `GET /staff-app/tables/:id`: อ่านสถานะครัวจาก `kitchen_order_items` (แถวล่าสุดต่อรายการ)
   - ตรวจก่อนว่าใน DB จริงไม่มี trigger ที่ sync สองตารางอยู่แล้ว
3. `GET /staff-app/menu/snapshot`: หมวด สินค้า SKU กลุ่มตัวเลือก และสถานะขายได้ ใน call เดียว บีบอัด และรองรับ `If-None-Match` ตอบ 304 เมื่อไม่เปลี่ยน
4. เทสต์ของทั้งสามข้อ

แอปที่ต่อ server รุ่นเก่า: ผังโต๊ะยังใช้ได้ (มีรายการแล้วแสดงเป็น "รออาหาร") ส่วนเมนูออฟไลน์ต้องมีข้อ 3
