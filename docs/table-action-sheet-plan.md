# แผน: เมนูโต๊ะแบบ modal จากด้านล่าง

สถานะ: ยืนยันแล้ว ใช้ข้อเสนอในหัวข้อ 7 ทุกข้อ
ทำขั้น 1–5 แล้ว ยังไม่ได้ลองจริงร่วมกับ iPad POS และมือถือลูกค้า (ขั้น 6)

## 1. ผลตรวจ API: ยังไม่ครบ

business logic ส่วนใหญ่มีใน `pos-services` แล้ว แต่ **md-staff เรียกไม่ได้** และมีหนึ่งอย่างที่ไม่มี API เลย

| ส่วนในรูป | บริการใน pos-services | md-staff เรียกได้ |
|---|---|---|
| ชื่อโต๊ะ, เวลาเปิด, ระยะเวลา | `staff-app/zones`, `tables/:id` (`opened_at`) | ได้ |
| สถานะอาหาร + "สั่งอาหาร" | `food_status` | ได้ |
| สั่งเพิ่ม | claim + `orders` | ได้ |
| บิล ฿ (ดูรายการและยอด) | `tables/:id` | ได้ (ดูอย่างเดียว) |
| จำนวนคน (แสดง) | `guest_count` | ได้ |
| **จำนวนคน (แก้ไข)** | **ไม่มี API** กำหนดได้ตอนเปิดโต๊ะเท่านั้น iPad POS มีฟังก์ชันเขียนลง Supabase ตรง (`pushGuestCountUpdate`) แต่ไม่พบจุดที่เรียกใช้ | ไม่ได้ |
| Mobile Order (QR) | `TableSessionService.getShareToken` / `createOrRefreshQR` | ไม่ได้ |
| ยกเลิกโต๊ะ | `TableSessionMutationService.closeSession` | ไม่ได้ |
| เปลี่ยนโต๊ะ | `transferTable` | ไม่ได้ |
| รวมโต๊ะ | `mergeTable` / `unmergeTable` | ไม่ได้ |

ที่เรียกไม่ได้เพราะ route `/api/v1/table-sessions/*` ใช้ `verifyToken` (JWT ของ staff)
ส่วน token ของ md-staff ลงนามด้วยคนละ secret และแอปทิ้ง JWT ของ staff หลัง login
จึงต้องเพิ่ม endpoint ใต้ `/api/v1/staff-app` ที่เรียก service เดิม

## 2. จุดที่ต้องระวัง

| # | สิ่งที่พบ | วิธีจัดการ |
|---|---|---|
| 1 | `closeSession` ไม่ดูออเดอร์ ถ้าปิดโต๊ะที่มีรายการ บิลจะค้างโดยไม่มีโต๊ะ (iPad POS ให้ยกเลิกเฉพาะโต๊ะที่ยังไม่มีออเดอร์) | endpoint ใหม่ตรวจใน transaction เดียวกับที่ปิด (ล็อก session) กันลูกค้าสั่งผ่าน QR แทรกเข้ามา |
| 2 | `createOrRefreshQR` เปลี่ยน token ทุกครั้ง QR ที่พิมพ์ให้ลูกค้าแล้วจะใช้ไม่ได้ | ใช้ `getShareToken` ซึ่งใช้ token เดิมถ้ายังไม่หมดอายุ (8 ชม.) |
| 3 | "รวมโต๊ะ" ของระบบคือเพิ่ม **โต๊ะว่าง** เข้ากลุ่มเท่านั้น รวมบิลสองโต๊ะที่มีลูกค้าไม่ได้ (`TABLE_ALREADY_MAPPED`) | ตัวเลือกในแอปแสดงเฉพาะโต๊ะว่าง ดูคำถามข้อ 3 |
| 4 | **บั๊กที่มีอยู่แล้ว:** ผังของ md-staff จับคู่ session กับโต๊ะหลักเท่านั้น โต๊ะที่ถูกรวม (เช่นรวมจาก iPad) จะแสดงว่าว่าง | จับคู่จาก `floor_items.active_session_id` และส่งว่าอยู่กลุ่มเดียวกับโต๊ะใด |
| 5 | claim ผูกกับโต๊ะ ไม่ใช่ session สองเครื่องถือคนละโต๊ะในกลุ่มเดียวกันได้ | claim และการแก้ไขต้องตรวจทุกโต๊ะในกลุ่ม |

ลิงก์ QR คือ `https://order.meedeepos.com/q/<token>` (ตาม iPad POS) ให้ server ส่ง URL มาเลย
ตั้งค่าได้ด้วย env แอปไม่ต้องรู้โดเมน

### จังหวะเรียก API
1. แตะโต๊ะ: เปิด modal ทันทีจากข้อมูลผังในเครื่อง
2. เรียก `tables/:id` หนึ่งครั้ง เพื่ออัปเดตยอดบิล จำนวนคน และผู้ถือโต๊ะ
3. claim เฉพาะตอนกดปุ่มที่แก้ข้อมูลหรือสั่งอาหาร การเปิดดูเฉย ๆ ไม่ล็อกโต๊ะ
4. แก้เสร็จ: อัปเดตผังหนึ่งครั้งและคืน claim (ยกเว้นเข้าหน้าสั่งอาหาร)

### ปุ่มตามสถานะ

| ปุ่ม | ว่าง | ยังไม่ได้สั่ง | มีรายการ | รอชำระเงิน | เครื่องอื่นถือ | ออฟไลน์ |
|---|---|---|---|---|---|---|
| สั่งอาหาร / สั่งเพิ่ม | ได้ | ได้ | ได้ | ปิด | ใส่ PIN | ปิด |
| บิล | ปิด | ได้ | ได้ | ได้ | ได้ | ปิด |
| จำนวนคน | ได้ | ได้ | ได้ | ปิด | ใส่ PIN | ปิด |
| Mobile Order | ได้ (เปิดโต๊ะ) | ได้ | ได้ | ปิด | ใส่ PIN | ปิด |
| ยกเลิกโต๊ะ | ปิด | ได้ | ปิด | ปิด | ใส่ PIN | ปิด |
| เปลี่ยน / รวม / แยกโต๊ะ | ปิด | ได้ | ได้ | ปิด | ใส่ PIN | ปิด |

โต๊ะงดใช้กดไม่ได้เหมือนเดิม

### ที่เสนอปรับจากรูป
- "ยกเลิกโต๊ะ" ใช้สีแดงและถามยืนยัน เพราะย้อนกลับไม่ได้
- ปุ่มที่ใช้ไม่ได้ให้จางลงแทนการซ่อน ตำแหน่งปุ่มจะไม่ขยับ พร้อมข้อความบอกเหตุผลเมื่อกด
- ปุ่มหลักใช้สี theme ของสาขา (แทนสีฟ้าในรูป) ปุ่มบิลใช้สีส้มตามรูป
- โต๊ะยังไม่มีรายการ ปุ่มหลักเขียน "สั่งอาหาร" มีรายการแล้วเขียน "สั่งเพิ่ม"
- ระยะเวลาคำนวณในเครื่องตอนเปิด modal

## 4. API ใหม่ (`/api/v1/staff-app`)

ทุกตัวต้องมี `X-Claim-Lease` ทุกตัวยกเว้น `guests` และ `qr` ต้องมี `Idempotency-Key` ด้วย
(สองตัวนี้ทำซ้ำได้ผลเดิมอยู่แล้ว) ใช้ `staff_id` จาก token เป็นผู้ทำรายการ
ทุกตัวยกเว้น `open` และ `qr` ต้องส่ง `session_id` ที่พนักงานเห็นอยู่
ถ้าโต๊ะเปลี่ยนลูกค้าไปแล้ว server ตอบ `TABLE_SESSION_CHANGED`
server ไม่คืน claim ให้ แอปคืนเองหลังทำรายการ

| Method | Path | การทำงาน |
|---|---|---|
| POST | `tables/:id/open` `{guest_count}` | เปิดโต๊ะว่าง (`openTable`) |
| PATCH | `tables/:id/guests` `{guest_count}` | **service ใหม่** เฉพาะ session ที่ `OPEN` |
| POST | `tables/:id/qr` | คืน `{url, expires_at}` จาก `getShareToken` |
| POST | `tables/:id/cancel` | ปิด session เมื่อไม่มีออเดอร์ ไม่งั้นตอบ `TABLE_HAS_ORDER` |
| POST | `tables/:id/transfer` `{destination_floor_item_id}` | `transferTable` + ย้าย claim ปฏิเสธถ้าปลายทางมีเครื่องอื่นถือ |
| POST | `tables/:id/merge` `{floor_item_id}` | `mergeTable` |
| POST | `tables/:id/unmerge` `{floor_item_id}` | `unmergeTable` |
| GET | `zones`, `tables/:id` | เพิ่มข้อมูลกลุ่มโต๊ะที่รวมกัน และแก้ข้อ 4 ในหัวข้อ 2 |

## 5. งานในแอป

- `table_action_sheet.dart`: modal ตามหัวข้อ 3
- ตัวเลือกโต๊ะปลายทาง (ใช้ตารางโต๊ะเดิม เลือกได้เฉพาะโต๊ะว่าง) สำหรับเปลี่ยนและรวมโต๊ะ
- หน้าต่างแก้จำนวนคน, หน้าแสดง QR (เพิ่ม package `qr_flutter`), กล่องยืนยันยกเลิก
- การ์ดโต๊ะที่รวมกันแสดงไอคอนและชื่อโต๊ะหลัก
- หน้ารายการที่สั่งเปิดได้โดยไม่ต้อง claim
- แตะโต๊ะแล้วเปิด modal แทนการ claim และเข้าหน้าเมนูทันที
- ต่อ server รุ่นเก่า: ปุ่มใหม่แจ้งว่าเซิร์ฟเวอร์ยังไม่รองรับ

| ขั้น | งาน | ตรวจด้วย |
|---|---|---|

| 4 | แอป: จำนวนคน, QR, ยกเลิกโต๊ะ | เทสต์ error แต่ละแบบ |

## 7. เรื่องที่ต้องตัดสินใจ

| # | คำถาม | ข้อเสนอ |
|---|---|---|
| 1 | แตะโต๊ะว่าง แสดง modal หรือเข้าหน้าเมนูทันทีแบบเดิม | แสดง modal เหมือนกันทุกโต๊ะ |
| 2 | ใครยกเลิก เปลี่ยน รวมโต๊ะได้ | พนักงานทุกคนที่ถือโต๊ะ ถามยืนยัน ใช้ PIN ผู้จัดการเฉพาะรับโต๊ะต่อ |
| 3 | รวมโต๊ะแบบ "เพิ่มโต๊ะว่างเข้ากลุ่ม" ตรงกับที่ต้องการไหม | ใช้ตามระบบเดิม การรวมบิลสองโต๊ะต้องออกแบบ server เพิ่ม ไม่อยู่ในแผนนี้ |
| 4 | ปุ่มบิลเปิดหน้ารายการที่สั่ง (ดูอย่างเดียว) | ใช่ การชำระและพิมพ์บิลทำที่ POS |
| 5 | ยกเลิกโต๊ะที่มีรายการแล้ว | ไม่ทำบนมือถือ ต้องยกเลิกบิลที่ POS (มีเรื่องสิทธิ์และใบยกเลิกเข้าครัว) |
